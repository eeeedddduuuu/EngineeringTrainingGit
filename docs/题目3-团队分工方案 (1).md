## 二、各角色详细职责

### P1：产品与项目负责人（PM）

> **不写核心代码，但必须理解每项技术。所有文档和协调的唯一出口。**

- 编写项目进度日志模板，督促全组填写

#### Day 1（下午）— 接口定稿 + 环境就绪

- 协调各角色之间的接口约定：
  - P2 ↔ P3：前端调用的 API 格式

- 起草工程实训报告框架，各角色按章节填内容

#### Day 2-3 — 并行开发 + 进度协调

- 跟踪各角色交付物 DDL 是否按时完成

#### Day 4（上午）— 收尾冲刺

### P3：后端开发

> **负责 API、数据库、权限、文件管理。整个系统的骨架，所有角色都依赖你。**

#### 数据库设计（核心表）

```sql
-- 用户表
users (id, username, password_hash, email, preferences JSON, created_at, updated_at)

-- 创作会话表
sessions (id, user_id, topic, target_audience, platform, duration, style, status, created_at)

-- 创作方案表（一次会话生成3个候选方案）
schemes (
    id, session_id, version_label,              -- version_label: "A"/"B"/"C"
    script_json JSON,                            -- 脚本内容
    storyboard_json JSON,                        -- 分镜表
    cover_text, hashtags,                        -- 封面文案、标签
    score FLOAT,                                 -- 方案评分
    rank INT,                                    -- 排名
    recommendation_reason,                       -- 推荐理由
    created_at
)

-- Agent 调用日志表
agent_logs (
    id, session_id, agent_name,                    -- agent_name: "热点分析"/"脚本创作"/"合规审查"/"发布策略"
    input_json JSON, output_json JSON,
    tools_called JSON,                            -- 调用了哪些工具
    latency_ms INT,                               -- 耗时
    tokens_used INT,                              -- Token消耗
    status,                                       -- success/failed
    error_message,
    created_at
)

-- 知识库条目表（供P5写入，前端搜索用）
knowledge_items (
    id, title, content, tags JSON, platform, source,
    source_url, collected_at, embedding_id
)

-- 审核记录表（进阶）
reviews (id, scheme_id, reviewer_id, status, comment, created_at)
```

#### API 设计（必做）

| 模块 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 用户 | POST | `/api/auth/register` | 注册 |
| 用户 | POST | `/api/auth/login` | 登录，返回 JWT |
| 用户 | GET | `/api/auth/me` | 获取当前用户信息 |
| 创作 | POST | `/api/creation/start` | 触发创作 → 返回 task_id |
| 任务 | GET | `/api/task/{task_id}/status` | 轮询任务进度/结果 |
| 方案 | GET | `/api/schemes?session_id=` | 获取某次会话的所有方案 |
| 方案 | GET | `/api/scheme/{id}` | 获取单个方案详情 |
| 对比 | POST | `/api/schemes/compare` | A/B 方案对比 |
| 历史 | GET | `/api/history?user_id=&page=&size=` | 分页获取历史会话 |
| 导出 | GET | `/api/export/{scheme_id}?format=md` | 导出 Markdown |
| 导出 | GET | `/api/export/{scheme_id}?format=docx` | 导出 Word |
| 统计 | GET | `/api/stats/samples` | 样例统计数据（供图表使用） |
| 知识库 | GET | `/api/knowledge/search?q=&top_k=5` | 知识库检索 |
| 审核 | POST | `/api/review` | 提交审核意见 |
| 审核 | PUT | `/api/review/{id}` | 修改审核意见 |

#### 技术要点

- **框架：** FastAPI + SQLAlchemy / SQLModel + Alembic（数据库迁移）
- **认证：** JWT 中间件，所有业务接口必须带 `Authorization: Bearer <token>`
- **密码：** bcrypt / passlib 哈希存储
- **文件上传：** 图片/视频/音频存本地 `uploads/` 目录，数据库只存路径
- **异步任务：** 创作接口是异步的——前端调用后立即返回 task_id，后端异步调用 Agent 工作流，前端轮询或 SSE 获取结果
- **CORS：** 配置允许前端跨域访问
- **日志：** Python logging，记录所有请求和异常
- **异常处理：** 统一异常响应格式 `{"error": "...", "detail": "..."}`
- **数据校验：** Pydantic 模型校验所有请求体

#### 交付物

- 完整后端代码（含所有 API 实现）
- 数据库建表 SQL 或 Alembic 迁移文件
- API 接口文档（FastAPI 自动生成的 Swagger UI 截图即可）
- 后端启动说明（依赖安装、数据库初始化、启动命令）

#### 必须接入的工具（≥3个）

| 序号 | 工具 | 实现方式 | 负责对接 |
|------|------|---------|---------|
| 1 | 知识库检索 | 调用 P5 的 `/api/knowledge/search` | P4 调 P5 |
| 2 | 网页搜索/抓取 | requests + BeautifulSoup 或搜索引擎 API | P4 自研 |
| 3 | 图片生成 API | DALL-E / Stable Diffusion API（进阶用） | P4 自研 |
| 4 | 敏感词过滤 | 本地敏感词库 + 正则匹配 | P4 自研 |
| 5 | 模板库 | 规则引擎，根据平台/时长匹配脚本模板 | P4 自研 |

#### Prompt 管理规范

- Prompt 不能硬编码在代码里——单独存放为 `prompts/` 目录下的 `.yaml` 或 `.json` 文件
- 每个 Agent 的 Prompt 包含：角色设定、能力边界、输入说明、工具使用指引、输出格式要求
- 保留 Prompt 迭代历史（v1 → v2 → v3），报告中展示优化过程

#### 候选方案评分算法（自研，不能用LLM直接说"这个好"）

建议设计量化评分维度，例如：

| 维度 | 权重 | 评分方式 |
|------|------|---------|
| 开头钩子吸引力 | 25% | LLM打分 1-10 |
| 结构与平台匹配度 | 20% | 规则检查 + LLM打分 |
| 目标受众匹配度 | 20% | LLM打分 |
| 内容原创性 | 15% | 与知识库相似度对比 |
| 可执行性 | 20% | 规则检查（时长、场景数合理） |

最终得分 = 各维度加权求和。

#### 技术选型建议

| | Dify 开源版 | Coze | 纯 LangChain |
|---|---|---|---|
| 部署方式 | Docker 自部署 | 云端 | 代码内嵌 |
| 可控性 | 高 | 低（黑盒） | 最高 |
| 工作流导出 | YAML | JSON | 代码即文档 |
| 开发速度 | 中 | 快 | 慢但有深度 |
| 答辩印象 | 好 | 一般（依赖平台） | 最好 |
| **推荐度** | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

> **强烈建议：** 至少部分 Agent 用 LangChain/LangGraph 自己写编排逻辑，答辩时能展示代码层面的设计能力。Dify 可以作为"我们先在 Dify 上做了原型验证"的技术探索环节。

### P5：数据/知识库 + 测试

> **负责 RAG 知识库搭建、样例数据采集与统计、全流程功能测试。**

#### 知识库建设

```
采集 → 清洗 → 分块 → Embedding → 存入向量库 → 提供检索接口
```

| 步骤 | 工具/方法 | 说明 |
|------|----------|------|
| **采集** | requests、BeautifulSoup、公开 API、人工整理 | 从公开来源收集创作相关素材 |
| **清洗** | Python 脚本 | 去重、格式化、提取元数据（标题/标签/平台/时间/来源） |
| **分块** | LangChain `RecursiveCharacterTextSplitter` | 每块 300-500 字，保留上下文重叠 |
| **Embedding** | `text-embedding-3-small` 或 `bge-large-zh-v1.5` | 将文本块转为向量 |
| **向量库** | Chroma（轻量易部署）或 FAISS | 存储向量并支持相似度检索 |
| **检索** | 相似度 Top-K + 可选 rerank | 返回最相关的知识条目及来源引用 |

#### 样例数据（≥30条）

每条样例至少包含以下字段：

| 字段 | 示例 |
|------|------|
| 标题 | "3个秋季护肤误区，你中了几个？" |
| 标签/类别 | 护肤、干货、好物推荐 |
| 平台 | 抖音 / 小红书 / B站 |
| 发布时间 | 2024-09-15 |
| 来源 | 抖音 @某某创作者 |
| 内容摘要/脚本概要 | 前3秒指出常见误区 → 逐一分析 → 推荐产品 |

#### 统计可视化（数据交付给 P2 展示）

- **样例主题分布：** 饼图/柱状图（护肤、美食、数码、旅行等各类占比）
- **平台分布：** 柱状图（抖音 vs 小红书 vs B站的样例数量对比）
- **发布时间趋势：** 折线图（按月统计样例发布数量）
- **内容标签词云：** 高频标签可视化

#### 测试职责

| 测试类型 | 具体内容 |
|---------|---------|
| **功能验收** | 对照 15 条基本要求逐项验收，确保全部达标 |
| **成功案例** | 至少 5 个，记录：输入参数 → Agent输出 → 耗时 → 质量评估 |
| **失败案例** | 至少 3 个，记录：输入 → 输出 → 失败原因分析 → Prompt/工作流优化过程 → 优化后结果 |
| **接口测试** | 所有 API 的正向/异常/边界测试（用 pytest + httpx） |
| **Agent 稳定性测试** | 相同输入反复调用 5 次，检查输出一致性 |
| **知识库检索测试** | 验证检索结果的相关性，记录 Top-1/3/5 的命中率 |
| **跨平台测试** | 验证同一主题在抖音/小红书/B站三个平台生成版本的差异 |

#### 失败案例模板

```
案例编号: F-001
输入: 主题="AI大模型技术解析" 受众="普通用户" 平台="抖音" 时长="30s"
输出: 技术术语过多，开头缺乏吸引力
原因分析: Prompt 未明确要求"面向零基础用户"的语言风格
优化方案: 在 Prompt 中增加「用小学生也能听懂的语言解释」
优化后结果: 生成内容通俗易懂，开头以"你手机里的AI"切入
```

#### 交付物

- 知识库构建说明文档（含架构图、技术选型理由）
- 样例数据集（CSV / JSON 格式）
- 统计图表数据及截图
- 测试报告（含 5 个成功案例 + 3 个失败案例的详细分析）
- 知识库检索效果评估（命中率、响应时间）

## 四、Git 分支策略

```
main
└── develop
    ├── feature/frontend       (P2)
    ├── feature/backend        (P3)
    ├── feature/agent          (P4)
    ├── feature/data-kb        (P5)
    └── feature/docs           (P1)
```

### 规范要求

| 规则 | 说明 |
|------|------|
| 分支命名 | `feature/角色-功能描述`，如 `feature/backend-auth-api` |
| 提交信息格式 | `feat(模块): 描述` / `fix(模块): 描述` / `docs(模块): 描述` / `test(模块): 描述` |
| 合并方式 | 功能分支 → develop，P1 review 后 merge |
| 每日同步 | 每天至少 merge develop 到自己分支一次，避免堆积冲突 |
| 提交频率 | 每人 ≥5 次有效提交，禁止一次性提交全部代码 |
| 最终版本 | Day 4 在 main 上打 tag `v1.0.0-final` |
| 记录导出 | 提交 `git_log.txt` `git_shortlog.txt` `git_branches.txt` `git_tag.txt` |

### 提交信息示例

```text
feat(auth): 完成注册登录接口
feat(agent): 增加知识库检索工具调用
fix(api): 修复方案导出Markdown格式错误
test(api): 增加权限校验测试用例
docs(readme): 补充环境配置和启动说明
feat(frontend): 完成创作工作台页面
feat(data): 完成30条样例数据采集和清洗
docs(report): 补充Agent工作流设计章节
```

| 费用项 | 平台/服务 | 预估金额 | 备注 |

| 搜索引擎 API | Bing API / 免费替代 | ¥0-30 | 可先用 requests 抓取替代 |

### 省钱策略

1. DeepSeek 价格极低（约为 GPT-4 的 1/50），作为主力模型
2. Embedding 模型使用 `bge-large-zh-v1.5` 本地运行，零成本
3. Dify 社区版 Docker 一键部署，无平台费
4. 图片生成使用 Stable Diffusion 免费 API 或本地部署
5. 网页抓取使用 `requests + BeautifulSoup`，不用付费搜索 API
